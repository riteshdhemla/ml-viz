# Agent2Agent Protocol (A2A)

## The problem it solves

[MCP](/wiki/model-context-protocol) lets one agent reach *tools*. But some sub-goals are best handed to a whole *other agent* — a specialist billing agent, a coding agent, a research agent — possibly built by a different team on a different framework. Hard-coding every such hand-off is the same $N \times M$ explosion MCP fought, one layer up: $N$ agents each needing bespoke glue to $M$ collaborators.

**A2A (Agent2Agent)**, introduced by Google in 2025, is an open standard for that **agent-to-agent** edge. It lets one agent **discover** another it has never been wired to, hand it a task, and receive results back — treating the remote agent as an *opaque collaborator*, not a function you call. The mental model: agents *hiring* agents.

<Callout type="info" title="A2A vs MCP — different edges, not competitors">
  MCP connects an agent **down** to tools and data. A2A connects agents **across** to peers. A single orchestrator typically uses **both**: MCP for its own tools, A2A to delegate a sub-goal. They stack; they do not compete.
</Callout>

## The four core concepts

Everything in A2A is built from four terms, each defined by its role in a delegation:

- **Agent Card** — a small JSON document an agent publishes at a well-known URL (`/.well-known/agent.json`). It advertises the agent's **identity**, its **skills** (what it can do), its **endpoint** (where to send work), and its **auth** requirements. This is how discovery happens *without* hard-coding: you fetch the card to learn what a stranger agent can do.
- **Task** — the unit of work, with an explicit **lifecycle**: `submitted → working → input-required → completed` (or `failed`). A task is stateful and can be long-running.
- **Message / Part** — a single turn *within* a task. A Message is made of **Parts**, and each Part carries one kind of payload: `text`, a `file`, or structured `data`. That is what makes A2A **multi-modal** by construction — you attach an image Part and a text Part in the same Message.
- **Artifact** — the *output* a task produces (a document, an image, a JSON record). Tasks return Artifacts, not just chat text.

Contrast with MCP: MCP's unit is a stateless *tool call* that returns immediately; A2A's unit is a stateful *Task* that can run for minutes and stream progress.

## A worked delegation trace

An orchestrator agent needs a refund issued. It has never been hard-coded to know the billing agent — it discovers it. Follow the four steps:

```jsonc
// 1. DISCOVER — orchestrator fetches the billing agent's card
//    GET https://billing.example.com/.well-known/agent.json
{"name": "Billing Agent",
 "skills": [{"id": "refund", "description": "Issue refunds for orders"}],
 "url": "https://billing.example.com/a2a",
 "capabilities": {"streaming": true}}

// 2. DELEGATE — orchestrator sends a Task via message/send (JSON-RPC)
{"jsonrpc": "2.0", "id": 1, "method": "message/send",
 "params": {"message": {"role": "user",
   "parts": [{"kind": "text", "text": "Refund order #4471"}]}}}

// 3. STREAM — billing agent pushes status updates over SSE
{"jsonrpc": "2.0", "id": 1, "result": {"status": {"state": "working"}}}
{"jsonrpc": "2.0", "id": 1, "result": {"status": {"state": "completed"},
  "artifacts": [{"parts": [{"kind": "text",
     "text": "Refunded $39.00 to order #4471 (txn r_88c2)"}]}]}}
```

Read the lifecycle in step 3: the state moves `working → completed`, and the final message carries an **Artifact** (the refund confirmation) rather than a plain reply. Because the card in step 1 advertised `"streaming": true`, the orchestrator knew to expect intermediate SSE updates instead of one blocking response. A more complex task might emit `input-required` mid-stream ("which card should I refund to?"), and the orchestrator would answer with another `message/send` on the same task.

## In code: publish a card, then delegate

The `a2a-sdk` handles the card, the well-known route, and the Task lifecycle. First, a specialist agent that advertises one skill:

```bash
pip install a2a-sdk uvicorn
```

```python
# billing_agent.py
from a2a.server.apps import A2AStarletteApplication
from a2a.server.request_handlers import DefaultRequestHandler
from a2a.server.agent_execution import AgentExecutor
from a2a.types import AgentCard, AgentSkill, AgentCapabilities

card = AgentCard(
    name="Billing Agent",
    description="Issues refunds for orders.",
    url="http://localhost:9000/a2a",
    version="1.0",
    capabilities=AgentCapabilities(streaming=True),
    skills=[AgentSkill(id="refund", name="Refund",
                       description="Issue refunds for orders",
                       tags=["billing"])],
)

class BillingExecutor(AgentExecutor):
    async def execute(self, context, event_queue):
        order = context.get_user_input()            # "Refund order #4471"
        await event_queue.enqueue_event(             # returns an Artifact
            context.new_text_artifact("result", f"Refunded {order} (txn r_88c2)"))
    async def cancel(self, context, event_queue): ...

app = A2AStarletteApplication(
    agent_card=card,
    http_handler=DefaultRequestHandler(agent_executor=BillingExecutor(),
                                       task_store=None),
).build()
# run: uvicorn billing_agent:app --port 9000
```

The SDK serves `card` at `http://localhost:9000/.well-known/agent.json` automatically. A client discovers it and delegates:

```python
import asyncio, httpx
from a2a.client import A2ACardResolver, A2AClient
from a2a.types import MessageSendParams, SendMessageRequest

async def main():
    async with httpx.AsyncClient() as http:
        card = await A2ACardResolver(http, "http://localhost:9000").get_agent_card()
        print(card.skills[0].id)                    # 'refund'  ← discovered, not hard-coded
        client = A2AClient(http, agent_card=card)
        req = SendMessageRequest(params=MessageSendParams(
            message={"role": "user",
                     "parts": [{"kind": "text", "text": "Refund order #4471"}]}))
        resp = await client.send_message(req)
        print(resp)                                 # Task → completed, with Artifact

asyncio.run(main())
```

`get_agent_card()` is step 1 of the trace; `send_message()` is steps 2–3.

## Security: an opaque peer is an untrusted peer

<Callout type="warning" title="Delegation crosses a trust boundary">
  A remote A2A agent runs code you don't own on inputs you can't fully see. Its Artifacts are untrusted content that may carry **indirect prompt injection**, and a compromised peer becomes a confused deputy acting with your orchestrator's authority. Authenticate agent cards, scope what you delegate, validate returned Artifacts before acting on them, and require human approval for irreversible outcomes (like an actual refund). See [Prompt Injection: Attack Taxonomy & Defenses](/wiki/prompt-injection-attacks-and-defenses).
</Callout>

## Common mistakes

1. **Only handling `completed`.** Long tasks emit `working` and `input-required`; a client that ignores the lifecycle will hang or silently drop work that was waiting on an answer.
2. **Confusing A2A with MCP.** A remote MCP endpoint is a *tool provider*; a remote A2A endpoint is an *autonomous agent*. Modeling one as the other loses either the tool-safety framing or the task lifecycle.
3. **Skipping card discovery.** Hard-coding a peer's endpoint and skills throws away the whole point — you re-introduce the bespoke coupling A2A exists to remove.
4. **Trusting Artifacts blindly.** Output from an opaque agent is untrusted input.
