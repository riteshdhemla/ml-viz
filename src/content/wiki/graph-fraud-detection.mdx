# Graph-Based Fraud Detection with GNNs

Feature-only fraud models evaluate each transaction in isolation. Graph-based models reason over the **connections** between accounts, devices, phone numbers, addresses, and IP addresses — detecting fraud rings and synthetic identities that look clean in isolation but reveal themselves through shared identifiers.

## The entity graph

Build a bipartite graph $G = (A \cup E, \text{edges})$ where:

- **Account nodes** $A$: each user/merchant/device account.
- **Entity nodes** $E$: shared identifiers (phone number, email domain, device fingerprint, IP /24 subnet, billing address).
- **Edges**: an edge $(a, e)$ exists if account $a$ is associated with entity $e$.

Two accounts connected through a shared entity have a **relationship signal**: accounts sharing a device ID are far more likely to be co-fraudulent than accounts sharing only a country.

## The homophily property

**Homophily** in social networks: similar nodes tend to connect. In fraud graphs: **fraud clusters**. An account connected to 3 known-fraud nodes via shared identifiers has a dramatically higher fraud probability than the same account's individual features would suggest.

This is the intuition behind GNN-based fraud detection: propagate fraud risk through the graph neighborhood.

## GraphSAGE for fraud

**GraphSAGE** (Hamilton et al., 2017) learns node representations by aggregating neighborhood features:

$$
\mathbf{h}_v^{(k)} = \sigma\!\left(W^{(k)} \cdot \text{CONCAT}\!\left(\mathbf{h}_v^{(k-1)},\; \text{AGG}\!\left(\left\{\mathbf{h}_u^{(k-1)} : u \in \mathcal{N}(v)\right\}\right)\right)\right)
$$

where the aggregator $\text{AGG}$ is typically mean or max pooling over the sampled neighborhood $\mathcal{N}(v)$.

**Layer interpretation:**
- Layer 0: account's own features (transaction history, account age, device info).
- Layer 1: aggregates features from directly connected entities.
- Layer 2: aggregates features from entity neighbors' account neighbors — capturing 2-hop relationships (accounts connected through shared entities).

A 2-layer GraphSAGE over the fraud graph captures the pattern: *account A shares a phone with entity E; entity E is connected to account B (known fraud)* → A's layer-2 representation includes B's risk signal.

## Relation-aware attention

Different edge types carry different fraud signals. A **Relation-Aware GNN** applies separate attention weights per relation type:

$$
\mathbf{h}_v^{(k)} = \text{AGG}_r\!\left(\left\{\mathbf{h}_u^{(k-1)} : u \in \mathcal{N}_r(v)\right\} \text{ for each relation } r\right)
$$

At Uber, the entity graph has relations: `SHARES_DEVICE`, `SHARES_PHONE`, `SHARES_EMAIL`, `SHARES_IP`. Each relation type has learned weights; sharing a device is a much stronger fraud signal than sharing an IP subnet, so the model learns to upweight device-sharing edges.

## A worked example — risk propagating 2 hops

Take a tiny graph. Three accounts carry an initial risk score (from their own features); two entity nodes are shared identifiers:

- **A** (risk **0.1**, looks clean) shares phone **P** with **B**, and device **D** with **C**.
- **B** (risk **0.9**, known fraud). **C** (risk **0.2**).

Run mean aggregation, one hop at a time:

**Layer 1 — entities average their accounts:**

$$
h_P = \tfrac{1}{2}(0.1 + 0.9) = 0.50, \qquad h_D = \tfrac{1}{2}(0.1 + 0.2) = 0.15
$$

**Layer 2 — account A averages its entities:**

$$
h_A = \tfrac{1}{2}(h_P + h_D) = \tfrac{1}{2}(0.50 + 0.15) = \mathbf{0.325}
$$

Account A's own features scored **0.1** — a feature-only model waves it through. But after two hops of message passing its representation is **0.325**, more than triple, *entirely* because it shares a phone with the fraudster B. That is fraud propagation: the signal traveled A ← P ← B even though A and B are never directly connected.

## In code — mean-aggregation message passing

The two layers above are just neighbor means over the bipartite graph. With `networkx` + `numpy`:

```bash
pip install networkx numpy
```

```python
import networkx as nx, numpy as np

G = nx.Graph()
risk = {"A": 0.1, "B": 0.9, "C": 0.2}          # account features
G.add_edges_from([("A", "P"), ("B", "P"),      # A & B share phone P
                  ("A", "D"), ("C", "D")])     # A & C share device D

def mean_agg(node, values):
    nbrs = list(G.neighbors(node))
    return np.mean([values[n] for n in nbrs])

# layer 1: entities aggregate accounts
h_entities = {e: mean_agg(e, risk) for e in ["P", "D"]}
# layer 2: accounts aggregate entities
h_A = mean_agg("A", h_entities)
print("entity risks:", {k: round(v, 3) for k, v in h_entities.items()})  # P=0.5, D=0.15
print("A after 2 hops:", round(h_A, 3), "(own feature was", risk["A"], ")")  # 0.325
```

A's propagated score jumps to 0.325 — the 2-hop cluster signal from the comparison table below. Production systems learn the aggregation weights instead of plain means; the standard library is `torch_geometric` (`from torch_geometric.nn import SAGEConv`), with relation-aware variants for the per-edge-type weighting described above.

## Handling label imbalance on graphs

Standard GNN training with cross-entropy over-fits to the majority class (not-fraud). Adaptations:

- **Focal loss** on node classification: down-weight easy not-fraud nodes.
- **GraphSMOTE**: oversample the subgraph around minority (fraud) nodes.
- **Positive-unlabeled (PU) learning**: treat unlabeled nodes as potentially positive rather than definitively negative, since fraud labels are noisy and incomplete.

## Incremental graph updates

A static graph trained on historical data misses real-time fraud signals. Production systems maintain **incremental graphs**:

1. New account created → add node with initial features.
2. Shared identifier detected → add edge between account and entity node.
3. Account labeled fraud by human review → update node label.
4. GNN re-scores neighbors of the newly labeled node immediately (subgraph re-inference, not full retrain).

Nubank's fraud graph update pipeline uses a streaming job (Flink) that updates entity-account edges as transactions arrive. When account $v$ is labeled fraud, all accounts within 2 hops are immediately re-scored using the pre-trained GNN on the updated subgraph.

## Comparison with feature-only models

| Scenario | Feature-only GBDT | Graph GNN |
|---|---|---|
| Fraud with unusual transaction pattern | ✅ Detected via features | ✅ Detected |
| Clean new account, shared device with fraud | ❌ Features look benign | ✅ 1-hop fraud propagation |
| Fraud ring with 50 accounts sharing phone | ❌ Each account looks independent | ✅ 2-hop cluster signal |
| Adversarial fraud using fresh identifiers | ✅ Behavioral features still signal | ❌ No graph signal yet |

Graph features and traditional features are complementary; production systems concatenate the GNN's node representation with hand-crafted velocity features and feed the concatenation to a GBDT scorer.
