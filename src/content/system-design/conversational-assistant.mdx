# Design a Conversational AI Assistant at Scale

<SystemDesignMeta
  track="Generative AI System Design"
  company="OpenAI / Anthropic"
  scale="100M+ users · multi-turn · streaming · safety-critical"
  difficulty="intermediate"
/>

A general-purpose chat assistant (ChatGPT/Claude-style) is the flagship
generative-AI *product*. The model is given — the system-design work is
everything **around** it: managing conversation context, grounding with
retrieval and memory, streaming responses, keeping it safe, and improving it from
feedback. It reads through the **agentic loop** (context → orchestration →
guardrails → operations).

## 1. Clarify the problem

- **Goal:** a helpful multi-turn assistant answering open-ended questions and
  doing tasks, for a huge user base, safely and affordably.
- **Key sub-problems:** long-conversation context management, factual grounding
  (reduce hallucination), safety, and cost/latency at scale.
- **Scope:** the product system around the LLM (context, retrieval, memory,
  safety, serving). Base-model training and raw serving infra are adjacent
  (see the LLM inference-serving case).

<Callout type="tip" title="Interview signal">
The model is a given — signal comes from the **context pipeline** (what goes into
the prompt), **safety**, and **the feedback loop**. Treat it as a product/systems
problem, not a modeling one.
</Callout>

## 2. Requirements & constraints

| Dimension | Target | Consequence |
|---|---|---|
| Latency | Stream first token fast | Streaming; model tiering |
| Context | Long multi-turn conversations | Summarization/truncation; memory retrieval |
| Grounding | Reduce hallucination | Optional RAG + tools + citations |
| Safety | Block harmful content/misuse | Input/output moderation, jailbreak defense |
| Cost | Frontier models are expensive | Route easy turns to smaller models; cache |

<ThinkFirst question="A conversation reaches turn 200; the context window fits 20. What's your strategy — and why is plain truncation wrong?">
Truncation silently drops the thread — the user's name, the constraint from
turn 3, the decision from turn 50. The working pattern is layered: keep
**recent turns verbatim**, roll older turns into a **running summary**, and
move durable facts into **retrievable memory** pulled in only when relevant.
The context window is a budget to allocate, not a buffer to overflow.
</ThinkFirst>

## 3. Context & memory *(spine: context)*

The heart of the product is **what fills the prompt**:

- **Conversation window:** recent turns verbatim; older turns **summarized** or
  truncated to fit the context budget without losing the thread.
- **Long-term memory:** durable user facts/preferences retrieved into context
  when relevant (RAG over the user's own history), not stuffed every turn.
- **Grounding tools:** optional retrieval (web/docs) and tools (calculator, code)
  when a turn needs facts or actions — with citations to curb hallucination.
- **System prompt:** the assistant's persona, policies, and capabilities.

## 4. Orchestration *(spine: orchestration)*

Per turn: assemble context (system prompt + memory + summarized history +
retrieved grounding) → decide if tools/retrieval are needed → generate a
**streamed** response → post-process (safety, citations). **Decoding strategy**
(temperature, top-p) trades determinism vs. creativity; tool-calling turns loop
through act→observe like an agent.

<SamplingViz />

Sampling parameters shape the assistant's "voice" — low temperature for factual
tasks, higher for brainstorming; the product often adapts them per intent.

<ThinkFirst question="Outputs are open-ended prose — there's no accuracy number. How do you decide a new model version is actually better?">
**Preference win-rate**: sample real prompts, generate with old and new, and
have humans (and a calibrated LLM judge) pick blind winners. Add targeted
checks the win-rate hides — groundedness when retrieval is used, refusal
correctness in both directions — and watch live signals (thumbs, regeneration
rate) after rollout. No single number; a panel of them.
</ThinkFirst>

## 5. Evaluation *(spine: evaluation)*

- **Quality:** helpfulness/correctness via **human preference** and **LLM-as-a-
  judge** on curated + live prompts; track win-rate against the previous version.
- **Faithfulness:** groundedness when retrieval is used (are claims supported?).
- **Safety:** refusal correctness (refuses harmful, doesn't over-refuse benign),
  jailbreak resistance.
- **Product metrics:** retention, thumbs up/down, regeneration rate.

## 6. Safety & guardrails *(spine: guardrails)*

- **Input moderation:** classify and block disallowed requests before generation.
- **Output moderation:** scan generations for harmful content, PII leakage.
- **Jailbreak/prompt-injection defense:** user text (and any retrieved content) is
  untrusted and must not override the system policy.
- **Refusal calibration:** helpful on benign edge cases, firm on genuinely harmful
  ones — measured, not vibes.

<WikiLink slug="prompt-injection-attacks-and-defenses" title="Jailbreak & injection defenses" />

<ThinkFirst question="Frontier-model inference on every turn for 100M users is ruinous. Where does most of the cost saving come from?">
From admitting most turns are easy: **route** them to a small, cheap model and
escalate only the hard ones — plus **prefix caching** for the shared system
prompt and response caching for repeated queries. Model tiering typically
saves more than any inference optimization, because the cheapest token is one
a frontier model never generates.
</ThinkFirst>

## 7. Operations *(spine: operations)*

- **Serving:** streaming, **model tiering** (small model for easy turns, frontier
  for hard), prompt/prefix caching — heavy overlap with the LLM inference-serving
  case.
- **Observability:** trace prompts, retrievals, tool calls, tokens, cost, latency,
  and feedback per conversation.
- **Feedback loop:** thumbs down, regenerations, and preference data drive RLHF/
  DPO alignment and prompt/policy updates — closing back into the product.

## 8. Tradeoffs & alternatives

| Choice | Alternative | Why |
|---|---|---|
| Summarize long history | Full history in context | Context is a finite, costly budget |
| Model tiering | One frontier model for all | Most turns are easy; tiering slashes cost |
| Optional RAG + tools | Rely on parametric knowledge | Grounding cuts hallucination & staleness |
| Layered moderation | Trust the model to self-police | Defense-in-depth; models can be jailbroken |

## 9. Interviewer follow-ups

<Details summary="A conversation exceeds the context window. What happens?">
Summarize older turns into a running synopsis and keep recent turns verbatim,
plus retrieve any specifically-referenced earlier content. Naive truncation drops
the thread; a rolling summary preserves it within the budget. Long-term facts live
in memory and are retrieved when relevant rather than kept in-window.
</Details>

<Details summary="How do you cut cost when most conversations are trivial?">
Route by difficulty: a small/cheap model handles easy turns and only escalates
hard ones to a frontier model, plus prompt/prefix caching for shared system
prompts. Most traffic is easy, so tiering is the biggest cost lever — measure the
quality delta per tier to set the routing threshold.
</Details>

<Details summary="A user tries to jailbreak the assistant into harmful output. Defenses?">
Layered: input moderation on the request, a system policy the user text can't
override, output moderation on the generation, and alignment training (RLHF/DPO)
for refusal behavior. Treat user (and retrieved) text as untrusted; no single
layer holds, so defense-in-depth plus continuous red-teaming is the answer.
</Details>

## Key takeaways

- A chat assistant is a **product/systems** problem around a given model — the
  **context pipeline**, **safety**, and **feedback loop** are where it's won.
- Manage long conversations with **summarization + retrieved memory**; ground with
  **RAG/tools** to cut hallucination.
- **Layered moderation + jailbreak defense** are mandatory, and **model tiering +
  caching** make it affordable at scale.
