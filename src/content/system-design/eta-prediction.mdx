# Design an ETA / Delivery-Time Prediction System

<SystemDesignMeta
  track="ML System Design"
  company="DoorDash / Uber"
  scale="millions of ETAs/min · <100ms · calibrated uncertainty"
  difficulty="intermediate"
/>

ETA prediction is the classic **real-time regression** interview: predict a
continuous arrival/delivery time, fast, per request, with **calibrated
uncertainty** because the number is shown to users and used to make dispatch
decisions. Walk it through the **ML project loop** — the twist versus a
classifier is that the *distribution*, not just the point estimate, matters.

## 1. Clarify the problem

- **Goal:** predict end-to-end delivery time (or ride ETA) at request time, and
  keep updating it as the trip progresses.
- **Why uncertainty:** a promised ETA is a commitment. Being *late* is worse than
  being *early*, so the loss is asymmetric and users need a reliable range, not a
  point guess.
- **Composed of stages:** e.g. food prep + courier assignment + drive time — each
  a sub-prediction that composes.
- **Scope:** the ETA model + feedback from actuals. Dispatch/assignment is
  adjacent (it *consumes* ETAs).

<Callout type="tip" title="Interview signal">
Decompose the ETA into its physical stages (prep, wait, transit) and predict
each — a single black-box regressor on total time is weaker and harder to debug
than a composed, interpretable estimate.
</Callout>

## 2. Requirements & scale

| Dimension | Target | Consequence |
|---|---|---|
| Latency | < 100 ms per request | Cheap model; precomputed spatial features |
| Volume | Millions of ETAs/min | Feature store + lightweight serving |
| Accuracy target | Low MAE *and* calibrated intervals | Quantile / probabilistic outputs |
| Freshness | React to live traffic, store load | Streaming features (courier supply, kitchen backlog) |

## 3. ML problem framing

**Regression with uncertainty** on spatial-temporal data. Predict a point
estimate (MAE/MAPE objective) *and* a predictive interval (quantile regression or
a probabilistic head). The asymmetric cost of lateness pushes the operating point
toward slightly conservative promises.

*What was breaking before?* A static "distance ÷ average speed" heuristic ignores
traffic, kitchen backlog, and courier supply; a point-only model can't express
the confidence the business needs to make promises.

## 4. Data & features *(spine: data)*

- **Labels:** observed actual times — abundant and low-latency (you learn the
  truth within an hour), the nice inverse of fraud's delayed labels.
- **Features:** origin/destination geo, historical segment speeds, live traffic,
  time-of-day/day-of-week, weather, **real-time supply/demand** (available
  couriers, kitchen backlog), and merchant-specific prep-time history.
- **Feature store:** the same streaming pipeline computes courier-supply and
  kitchen-load features for train and serve to avoid skew.

## 5. Model *(spine: hypothesis space + objective)*

- **Baseline:** GBDT (LightGBM) on the engineered features with a quantile loss —
  strong, fast, and the production default for tabular spatial-temporal
  regression.
- **Add:** graph/embedding features for road segments; deep models where
  sequence/route structure pays off.
- **Uncertainty:** quantile regression (predict P10/P50/P90) or a distributional
  output; the shown ETA is a chosen quantile, not the mean.

## 6. Serving & scaling

Fetch precomputed + streaming features, run the composed models (prep + transit),
sum with uncertainty propagation, and return an ETA + range under 100ms.
Re-predict as the trip progresses (courier assigned, en route) so the number
tightens over time.

## 7. Evaluation *(spine: evaluation)*

- **Point accuracy:** MAE / MAPE, and **asymmetric** metrics (lateness rate,
  minutes-late) that reflect the real cost.
- **Calibration of intervals:** does the P90 actually cover 90% of actuals? A
  reliability check on the quantiles is essential.
- **Online:** A/B on user-facing outcomes (order completion, satisfaction,
  support contacts about late orders), not just MAE.

## 8. Monitoring & feedback *(spine: feedback)*

- **Fast loop:** actuals arrive quickly, so drift (new traffic patterns, a
  merchant's kitchen slowing down) is caught and retrained on rapidly.
- **Regime shifts:** weather events, holidays, surges — monitor segment-level
  error and keep event features fresh.

## 9. Tradeoffs & alternatives

| Choice | Alternative | Why |
|---|---|---|
| Composed stage models | Single end-to-end regressor | Interpretable, debuggable, each stage improvable |
| Quantile / probabilistic output | Point estimate only | The business needs calibrated ranges to make promises |
| GBDT baseline | Deep model first | Tabular spatial-temporal → GBDT is strong and cheap |
| Streaming supply features | Static averages | Live courier/kitchen load is the biggest error driver |

## 10. Interviewer follow-ups

<Details summary="Users complain deliveries are 'always late.' MAE looks fine. What's wrong?">
MAE is symmetric but the cost isn't. A model minimizing MAE promises the median,
so ~50% of orders are late. Predict and display a higher quantile (e.g. P70–P90)
so promises are conservative, and track lateness rate, not just MAE.
</Details>

<Details summary="A kitchen suddenly slows down at lunch. How does the ETA adapt?">
Streaming merchant-load features (live backlog, recent prep times) feed the prep-
time sub-model, so ETAs lengthen within minutes. Static historical averages would
lag the regime change entirely — this is why the feature store must be real-time.
</Details>

<Details summary="How do you keep the ETA accurate as the trip progresses?">
Re-predict at each milestone (order placed → courier assigned → picked up → en
route). Uncertainty shrinks as more is known; the transit sub-model switches from
a prior to live GPS-based estimation once the courier is moving.
</Details>

## Key takeaways

- ETA is **real-time regression with calibrated uncertainty** — the *interval*
  matters because the number is a promise.
- **Compose** the estimate from physical stages (prep, wait, transit) for
  accuracy and debuggability.
- **Asymmetric lateness cost** means predicting a conservative quantile, not the
  mean; **fast actuals** make drift easy to catch and retrain on.
