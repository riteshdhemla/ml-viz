# Design an Autonomous Coding Agent

<SystemDesignMeta
  track="Agentic System Design"
  company="Claude Code / Devin"
  scale="large repos · sandboxed execution · test-driven loop"
  difficulty="advanced"
/>

A coding agent is the agentic interview where **the environment does the
verification**: the agent can *run the code* and read the result, so the design
centers on a tight **plan → edit → run tests → observe** loop with a real
feedback signal. It is also the domain with the clearest public evidence of what
works: on SWE-bench — 2,294 real GitHub issues from 12 Python repositories —
the best 2023 systems resolved under 2% of tasks
([Jimenez et al.](https://arxiv.org/abs/2310.06770)); by late 2024 a
deliberately *simple* agent around Claude 3.5 Sonnet resolved 49% of SWE-bench
Verified ([Anthropic](https://www.anthropic.com/engineering/swe-bench-sonnet)).
Walk it through the **agentic project loop** — context and orchestration are
where it's won, and tests give evaluation for free.


## R: Requirements *(spine: task)*

**Functional.**

- **Goal:** given an issue / feature request, produce a correct code change
  (edits + tests) in a real repository — ideally a passing PR.
- **When it acts vs. stops:** iterate until tests pass or a step/time budget is
  hit; escalate on ambiguous requirements or destructive operations.
- **Success:** tests green + task actually solved (not just tests deleted) +
  reasonable, reviewable diff.
- **Scope:** the agent loop over a sandboxed repo. Adjacent: the CI/review system
  it hands off to.

**Non-functional.**

| Dimension | Target | Consequence |
|---|---|---|
| Repo scale | Large, unfamiliar codebases | Retrieval over the repo, not whole-repo in context |
| Safety | Runs arbitrary code | Isolated sandbox, no prod creds, network limits |
| Latency/cost | Minutes/task, bounded | Step budget; model tiering; cache builds |
| Reliability | Doesn't wreck the repo | Diff review, reversible changes, test gate |

<Callout type="tip" title="Interview signal">
"The agent can execute code, so verification is grounded — tests are the reward
signal." Naming the executable environment as the core asset separates a coding
agent from a code-*completion* model.
</Callout>

## E: Estimation

Assumptions stated so they can be challenged:

| Quantity | Assumption | Result |
|---|---|---|
| Load | 10K tasks/day | ~7 tasks starting per minute |
| Steps | ~50 model calls per task | 500K model calls/day |
| Context per call | ~20K tokens (task, retrieved code, recent history) | ~1M input tokens per task ≈ 10B/day |
| Output | ~500 tokens per call | ~25K output tokens per task ≈ 250M/day |
| Sandboxes | ~15 minutes of container time per task | 2,500 container-hours/day ≈ 100 sandboxes live on average |
| Eval | 500 tasks × ~50 calls × 3 trials per candidate release | ~75K model calls per full eval run |

Two things follow. Input tokens dominate by ~40×, because every step re-sends
the context, so **prompt caching** of the stable prefix (task, repo summary)
is the largest cost lever. And the sandbox fleet, not the model, sets the
concurrency ceiling, so container start time and build caches are design
concerns.

## S: Storage schema

| Entity | Key fields | Store |
|---|---|---|
| Task | id, repo, base commit, issue text, budget, status | relational DB |
| Sandbox snapshot | task id, container image, build/dependency cache | image registry + blob cache |
| Trajectory step | task id, step #, tool, arguments, result (truncated), tokens, cost, latency | append-only trace store |
| Patch | task id, diff, tests run + results, PR URL | relational DB + git host |
| Eval case | task id, hidden fail-to-pass tests, expected behavior | versioned eval store (never mounted in the sandbox) |

The trajectory log is the most important table: it is the debugging record,
the cost ledger, and the raw material for the eval set. Hidden tests live
somewhere the agent's sandbox can never read.

## H: High-level design *(spine: orchestration)*

```
issue ──► task service ──► orchestrator (agent loop, budgets, stop conditions)
                             │  ▲
                   model calls│  │observations
                             ▼  │
           model gateway (tiering, prompt cache)      tool executor ──► sandbox (repo checkout)
                                                      code search / symbol index
          trace store ◄── every step                  verifier: build + tests
          PR creator ──► human review / CI
```

The loop is **plan → edit → run → observe → reflect**:

1. Understand the task; locate the relevant code (retrieval).
2. Make an edit.
3. **Run the tests / build**: the grounded feedback signal.
4. Read failures; reflect and fix; repeat until green or budget hit.

<ThinkFirst question="SWE-bench solve rates jumped from under 2% to ~50% in about eighteen months — on the same benchmark. Models improved, but that's not the whole story. What else was being engineered?">
The **agent–environment interface**. SWE-agent showed that with the *same*
model, redesigning how the agent views files, searches, and edits code lifted
solve rates several-fold (to 12.5% pass@1) — the interface, not the model, was
the bottleneck. Anthropic's 49% run pushed the opposite lesson to its limit: a
minimal scaffold with two general-purpose tools, letting a stronger model
drive. Both agree on the design principle: an agent is a model *plus* an
environment you control, and the environment is your half of the work.
</ThinkFirst>

## A: APIs

- **Tools:** `read_file`, `edit_file`, `run_shell` / `run_tests`, `search_code`,
  `git` — typed and sandboxed. Execution is a first-class tool, not an
  afterthought.
- **Interface design matters as much as tool choice.** The SWE-agent paper
  ([Yang et al.](https://arxiv.org/abs/2405.15793)) calls this the
  **agent–computer interface (ACI)**: compact search results instead of pages of
  hits, a file viewer showing ~100 lines at a time, and an edit command that
  runs a linter and *rejects malformed edits with feedback* — each measurably
  moved the solve rate. Anthropic's SWE-bench scaffold went further in the
  minimal direction: essentially a bash tool and a string-replacement edit tool,
  with the model deciding everything else
  ([Anthropic](https://www.anthropic.com/engineering/swe-bench-sonnet)).

```
edit_file(path: str, old_str: str, new_str: str) -> {ok, lint_errors[], diff}
run_tests(selector?: str, timeout_s: int = 600) -> {passed, failed[], output_tail}
search_code(query: str, k: int = 20) -> [{path, line, snippet}]
```

Every tool runs inside the sandbox, returns truncated, structured output, and
reports errors as observations the model can act on rather than exceptions that
end the run. Externally the service exposes one call,
`POST /tasks {repo, commit, issue}`, and streams status until a PR URL or an
escalation comes back.

<ThinkFirst question="The repo is millions of lines and the context window holds a fraction of it. How should the agent decide what to read?">
Retrieval, not stuffing: code search (lexical + embedding), symbol lookup, and
the dependency graph surface a small relevant set, and the agent explores
incrementally from there — open a file, follow references. Context is a budget
to *spend*, not fill; the design question is what earns its place in it. The
agent loop is exactly this discipline: gather context → take action → verify,
repeated ([Anthropic](https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk)).
</ThinkFirst>

## D: Detailed design *(spine: context + guardrails)*

### Context engineering

- **Repo retrieval:** the codebase is too large for the context window — retrieve
  relevant files via code search (lexical + embedding), the dependency graph, and
  symbol lookup. Feed *targeted* context, not the whole repo.
- **Environment:** an isolated container with the repo checked out; the agent's
  actions (edits, commands) mutate it.

<ThinkFirst question="The agent has made three edits and the same test still fails with the same error. What should the harness do that a naive retry loop wouldn't?">
Detect the stuck state and force a change of strategy. Repeated identical
failures mean the agent's model of the bug is wrong — the harness should feed
the full failure history back, prompt an explicit re-diagnosis (reflection)
rather than another blind edit, and if the loop persists, stop and escalate.
Budgets exist precisely because an agent that can't tell it's stuck will
happily burn the whole budget on one wrong theory.
</ThinkFirst>

### Orchestration details

- **Reflection on failure:** feed the test output back so the model diagnoses,
  rather than blindly re-editing.
- **Step budget & stop conditions:** cap iterations; stop on green, on repeated
  identical failures (stuck), or on ambiguity → escalate.
- **Keep the topology simple.** Anthropic's guidance is to start with a single
  augmented loop and add structure only when it measurably helps
  ([Anthropic](https://www.anthropic.com/engineering/building-effective-agents)).
  Cognition (Devin) goes further for code: parallel sub-agents making *edits*
  tend to make conflicting implicit decisions, because each holds a partial
  context, so keep write-actions single-threaded and share full context
  ([Cognition](https://cognition.ai/blog/dont-build-multi-agents)). Sub-agents
  are safest for read-only work: exploring the repo, reproducing the bug.

<ThinkFirst question="This agent runs arbitrary generated shell commands. Sketch the threat model before reading on.">
Three distinct threats: **destructive actions** (rm -rf, force-push, dropping a
database), **exfiltration** — a malicious file or issue comment prompt-injects
the agent into leaking secrets, and **runaway resource use**. Each maps to a
different control: sandbox + no prod credentials, treating all repo/issue text
as untrusted input, and hard resource/step caps — plus every change landing as
a reviewable PR, never a direct push.
</ThinkFirst>

### Guardrails & safety *(spine: guardrails)*

- **Sandbox everything:** no production credentials, restricted network, resource
  limits — it runs arbitrary generated code.
- **Reversibility:** changes land as a branch/PR a human reviews, never a direct
  push to main.
- **Prompt injection:** repo content, issue text, and dependency output are
  untrusted — a malicious file must not exfiltrate secrets or run unsafe commands.

### Operations *(spine: operations)*

- **Tracing:** log every tool call, edit, and test result — essential for
  debugging non-deterministic runs and for the eval set.
- **Cost/latency:** tier models (cheap for navigation, strong for hard reasoning),
  cache builds/deps, parallelize independent read-only sub-tasks.
- **Feedback:** failed/abandoned tasks become eval cases and prompt improvements.

<ThinkFirst question="The agent reports “all tests pass.” In how many ways can that claim be hollow?">
At least three: it deleted or weakened the failing tests (reward hacking), it
overfit to the visible tests without solving the actual issue, or it got lucky
on a flaky suite. That's why SWE-bench grades against **held-out fail-to-pass
tests** the agent never sees, and why your own eval needs protected tests plus
trajectory checks: did it edit sensible files, run tests before claiming done?
</ThinkFirst>

## E: Evaluation *(spine: evaluation)*

### Evaluating the agent

- **Outcome:** does the change pass the *hidden/held-out* tests and actually solve
  the issue? SWE-bench measures exactly this; **pass@k** captures the
  retry-until-solved reality.
- **Benchmark hygiene:** the original SWE-bench contained under-specified issues
  and broken tests that unfairly penalized correct patches — SWE-bench Verified
  is a 500-task subset screened by human annotators to fix this
  ([OpenAI](https://openai.com/index/introducing-swe-bench-verified/)). The
  lesson generalizes: audit your eval set before trusting movement on it.
- **Trajectory:** did it edit the right files, run tests before claiming done, and
  avoid thrashing? Catches agents that "pass" by gaming or luck.
- **Guard against reward hacking:** an agent that deletes failing tests "passes" —
  eval must use protected tests it can't modify.

<ThinkFirst question="A full eval run is 500 tasks × dozens of model calls each, and two identical runs give different scores. How do you make the numbers trustworthy without unbounded spend?">
Report across **multiple trials** (pass@k or mean ± spread), never a single
run — agent variance easily swamps a 2-point "improvement." Contain cost with
a fixed cheap smoke subset for every change and the full suite only for
candidate releases. And trace everything: when the score moves, per-task
trajectories tell you *which* tasks flipped and why — without traces, a
regression is just a number.
</ThinkFirst>

### Does the design meet the requirements?

- **Repo scale:** retrieval plus a 100-line file viewer keeps each call near
  the ~20K-token budget from the estimate, however large the repo.
- **Safety:** sandbox, no production credentials, and PR-only output bound the
  worst case to a rejected pull request.
- **Cost:** the step budget caps a runaway task at a known spend; prompt caching
  attacks the dominant input-token term.
- **Bottleneck:** sandbox start time and test-suite duration, not model
  latency, set end-to-end task time. Warm pools and dependency caches are where
  latency work pays.

### Tradeoffs & alternatives

| Choice | Alternative | Why |
|---|---|---|
| Retrieve repo context | Stuff whole repo in context | Repos exceed context; retrieval is cheaper and sharper |
| Test-driven loop | Generate-and-hope | Execution gives a real, groundable reward signal |
| Minimal general tools | Many specialized tools + rigid workflow | Simple scaffolds transfer; ACI quality beats tool count |
| Single-threaded writes | Parallel editing sub-agents | Partial-context workers make conflicting decisions |
| PR + human review | Auto-merge | Reversibility and trust; code is high-stakes |
| Protected test eval | Any tests pass | Prevents reward hacking (deleting tests) |

## D: Distinctive component

**The executable environment as verifier.** What separates a coding agent from
every other agent in this section is that its world can *check its work*: the
sandbox runs the build and the tests, so each step's feedback is ground truth
rather than another model's opinion. Three design consequences follow.

1. **The ACI is product surface.** Search output, the file viewer, and a
   lint-gated edit command decide how well the model can use that verifier.
   SWE-agent's interface changes moved the solve rate several-fold on the same
   model.
2. **Verification must be tamper-proof.** The tests that grade the work live
   outside the sandbox, so the agent cannot pass by editing them.
3. **The verifier sets latency.** A task takes as long as its builds and test
   runs, so warm containers and dependency caches buy more speed than a faster
   model.

## Interviewer follow-ups

<Details summary="The agent 'passed' by deleting the failing test. How do you prevent it?">
Evaluate against protected, hidden tests the agent can't see or modify, and diff-
check that it didn't weaken the test suite. Reward hacking is the defining failure
mode of code agents — the eval, not the agent, must own the ground-truth tests.
This is exactly how SWE-bench grades: held-out fail-to-pass tests applied after
the agent finishes.
</Details>

<Details summary="The repo is millions of lines. How does the agent find the right code?">
Retrieval: code search (lexical + embedding), symbol/definition lookup, and the
dependency graph surface a small relevant set. The agent explores incrementally
(open a file, follow references) rather than loading everything — context is a
budget to spend, not fill.
</Details>

<Details summary="Would you use multiple agents in parallel to go faster?">
Only for read-only work (exploration, reproduction, review). Parallel sub-agents
that *edit* hold partial context and make conflicting implicit decisions — the
failure mode Cognition documents from building Devin. Keep writes
single-threaded with full shared context; buy speed with caching and model
tiering instead.
</Details>

<Details summary="How do you keep it from running something destructive?">
Sandbox with no prod access, restricted network, and resource caps; require
confirmation or block destructive shell patterns; land changes as a reviewable
branch. Treat all repo/issue text as untrusted input that cannot escalate the
agent's permissions.
</Details>

## Key takeaways

- A coding agent's superpower is a **sandboxed executable environment** — tests
  are a grounded reward signal for a **plan → edit → run → reflect** loop.
- The **agent–computer interface** is a measured, first-order lever: SWE-agent's
  ACI redesign and Anthropic's two-tool 49% SWE-bench Verified scaffold both
  show the environment matters as much as the model.
- **Repo retrieval** (not whole-repo context) and **reflection on test failures**
  drive success; **step budgets** and stuck-detection prevent thrashing.
- Evaluate on **protected tests** (pass@k, multiple trials) to stop reward
  hacking, and keep every change **sandboxed and reversible**.
