# Security Audit

Run a security review of the ml-viz codebase. This is an educational site — the attack surface is limited, but the risks below are real.

## Areas to audit

### 1. MDX / Content injection (highest priority)
The site renders user-authored MDX via `next-mdx-remote`. Check:
- `LessonLayout.tsx`: confirm `blockJS: true` is set in MDXRemote options — this is the critical guard against arbitrary JS execution in lesson content
- `mdxComponents.tsx`: confirm the component map only exposes safe, controlled components (no `<script>`, `<iframe>`, `dangerouslySetInnerHTML>` passthrough)
- No lesson `.mdx` file contains raw `<script>` tags, `javascript:` URLs, or `dangerouslySetInnerHTML`
- Callout and Exercise components do not pass raw MDX content to `dangerouslySetInnerHTML`

### 2. External URLs and open redirects
- `NotebookLink.tsx` and any other component that renders an `<a href>` pointing to user-controlled data — confirm `href` values are validated or come only from the server-side registry (not user input)
- Colab links are generated by `getNotebookUrl()` — confirm the GitHub repo/branch values are hardcoded, not interpolated from URL params or MDX frontmatter
- If `notebookUrl` is allowed in frontmatter, confirm it can only be an `https://` URL (not `javascript:` or `data:`)

### 3. Dependency vulnerabilities
Run: `npm audit --audit-level=moderate`
Flag any `moderate` or higher severity findings. Note: do not auto-fix with `npm audit fix --force` as it may introduce breaking changes.

### 4. Next.js route safety
- `dynamicParams = false` is set on course and lesson pages — confirms unknown slugs 404 instead of hitting the filesystem with arbitrary paths
- `getLessonContent()` in `content.ts` constructs a file path from URL params — confirm it uses `path.join` (which normalises `../` traversal) and does not allow escaping `CONTENT_DIR`
- No API routes exist that accept user input and write to the filesystem

### 5. Environment variable exposure
- Confirm no secrets are in `NEXT_PUBLIC_` variables (those are bundled into client JS)
- `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID` must only be in GitHub Secrets, never in `.env` files committed to the repo
- Check `.env.example` — it should only contain non-sensitive placeholder values

### 6. Third-party script safety
- Check `src/app/layout.tsx` for any `<Script>` tags — verify they use `strategy="lazyOnload"` or `"afterInteractive"`, not `dangerouslyAllowSVG`
- KaTeX CSS is loaded via a `<link>` tag — confirm it points to an integrity-hashed CDN URL or is self-hosted

### 7. Zustand persistence
- `useProgress` uses `localStorage` via Zustand `persist` — confirm the persisted data is never eval'd or injected into the DOM as HTML

## Output format

```
[CRITICAL] src/... — <description of vulnerability and fix>
[HIGH]     src/... — ...
[MEDIUM]   src/... — ...
[INFO]     src/... — no issue, confirmed safe
```

After auditing:
1. Fix any `[CRITICAL]` or `[HIGH]` items immediately
2. Report `[MEDIUM]` items with recommended fixes for the user to approve
3. Leave `[INFO]` lines as confirmation of what was verified safe
4. Run `npm run build` to confirm fixes don't break the build
